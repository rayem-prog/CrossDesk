用户选择的下一个功能：**Mac / Windows 任意普通文件双向复制粘贴，包括 PDF、Office 文档、压缩包等**。

## 结论与验证边界

当前图片互传可以作为后续功能的基础，但有两项复制事件识别问题。仓库保留的旧文件传输路径还有四项可复现的数据完整性、缓存和资源控制问题，不能直接通过放开文件扩展名或开启旧环境变量作为新功能交付。

- 原项目 `cargo test --locked --no-default-features`：48 项通过。
- `cargo fmt --check`：通过。
- `cargo check --locked --no-default-features --target x86_64-pc-windows-gnu --tests`：通过。
- 在独立源码副本追加 6 个行为回归测试：6 个均失败，并分别复现下面的问题；原项目工作区保持干净。这些是审查新增测试预期发现的缺陷，不是原有 48 项测试失败。
- 新增测试只使用内存剪贴板边界、环回加密 TCP 和独立临时文件，不读取或覆盖用户日常剪贴板。
- Windows 原生运行、真实双机粘贴、系统休眠和具体应用兼容性仍未验证；交叉编译不能替代这些验收。
- 范围覆盖图片会话、Windows/Mac 剪贴板适配、加密传输、客户端/Windows 服务端接入、旧文件模块和现有构建入口；不是对全部原生输入后端和 GUI 的全面审计。

证据：[回归日志](CrossDesk-0.2.0-review-regressions.log)、[仅用于审查的测试补丁](CrossDesk-0.2.0-review-regressions.patch)、[复现脚本](CrossDesk-0.2.0-review-reproduce.py)。

## 发现的问题，按修复优先级排列

### R1 · P1：发布远端图片后，紧接着的新本地复制可能被吞掉

位置：[src/clipboard/session.rs:288](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/clipboard/session.rs:288>)；相关观察状态更新在 155–157 行。

`write_if_current` 返回成功后，代码另外读取系统剪贴板版本，再把此时的读回内容指纹加入“远端内容”集合。原生写入完成到读取版本之间，其他应用可能已经复制了另一张图片 B。这样会把 B 的版本当作远端发布版本，把 B 的指纹当作回传；下一轮既看不到版本变化，也会压掉 B。

复现：测试在原生发布边界注入“远端 A 发布后立即本地复制 B”，结果返回 `Some(2)`，B 被加入远端抑制集合，`should_send(B)` 为 false。

修复要求：发布结果携带属于本次写入的版本/身份；读回内容必须与本次远端内容一致，才可登记为回传。遇到不同内容或不确定的版本，保留为待观察的本地事件，不能推进到它的版本并把它加入远端集合。Windows 尽量在原生剪贴板锁释放前获取本次发布版本；Mac 适配器需要返回写入身份并校验读回，不能任意信任写入结束后的快照。

验收：远端 A 写入后、本地 B 在发布返回前或返回后出现，两种时序都必须只把 B 发到对端一次。

### R2 · P1：旧文件接收会把不完整文件作为完成结果返回

位置：[src/file_transfer.rs:97](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/file_transfer.rs:97>)；消费者见 [src/client.rs:142](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/client.rs:142>)、[src/server/windows.rs:335](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/server/windows.rs:335>)。

旧 `finish()` 直接丢弃当前文件状态，不检查剩余长度；消费者收到 `DragEnd` 后直接把返回路径发布到剪贴板。`FileEnd` 也没有参与完整性验收。

复现：声明 `report.pdf` 有 10 字节，只发送 3 字节，再调用完成，返回的文件实际只有 3 字节。源文件在发送时缩短、异常提前结束，都会使接收结果不可靠。

影响范围：旧文件模式，默认图片模式未启用此路径。

修复要求：整组清单、每个文件的长度/摘要及明确结束状态都验证成功后才发布；异常结束必须拒绝整组并清理暂存文件。接收完成应是可失败的操作，不能用路径列表代表成功。

### R3 · P1：旧文件缓存会被下一批传输提前删除

位置：[src/file_transfer.rs:107](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/file_transfer.rs:107>)。

所有旧文件批次共用 `deskbridge-received`，下一批启动就 `remove_dir_all`。上一批仍被系统剪贴板引用时，如果下一批中途失败、用户尚未粘贴或文件管理器正在复制，引用会失效。

复现：完成并发布 `old.pdf`，再开始 `next.pdf`，上一批返回的 `old.pdf` 路径马上不存在。

影响范围：旧文件模式。

修复要求：每批使用独立目录，正在接收的 `.part` 和已发布缓存分开管理；新批次不得删除旧批次。缓存清理需保护当前剪贴板引用与正在使用的目录。原生文件管理器开始粘贴后的持有时间需要实机验证，不应声称可以立即回收。

### R4 · P1：旧文件模式中，同名文件静默覆盖

位置：[src/file_transfer.rs:123](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/file_transfer.rs:123>)；发送端 basename 映射在 149–156 行。

选择不同文件夹下同名的两个文件时，都被映射到相同相对路径，接收端 `File::create` 会截断已有文件。根文件集合还会合并相同路径，最终只返回一个结果。

复现：依次传两个 `report.pdf`，内容为 `first` 和 `second`，最后仅剩一个文件，内容为 `second`。

影响范围：旧文件模式。

修复要求：清单内确定性重命名，例如 `report.pdf`、`report (2).pdf`；实际创建时使用排他创建，处理 Windows 大小写和 macOS Unicode 等价名称冲突。不能仅靠字符串集合保证不覆盖。

### R5 · P2：重新复制同一张图片，不能作为失败后的重试

位置：[src/clipboard/session.rs:176](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/clipboard/session.rs:176>)；`SyncState::should_send` 在 19–20 行。

发送侧按上一次内容指纹去重，只要内容相同，即使系统剪贴板已经产生新的复制版本，也不再发送。发送成功日志只表示写入连接，接收端可能因为本地有新复制而跳过。此时 README 建议“重新复制”重试，但相同图片仍被压掉；也没有接收结果确认来清除该状态。

复现：真实环回加密连接中，同一工作线程先发送 A；本地版本增加并明确再次复制 A，第二次读帧超时，未发送。

修复要求：区别“同一个系统剪贴板版本被重复轮询”和“用户再次复制相同内容”。以复制事件版本/来源身份识别远端回传；明确的再次复制允许重新发送。另加接收结果确认，区分已传完、已发布、因新本地复制跳过和失败。

### R6 · P2：旧文件接收端没有强制总量、单文件或数量上限

位置：[src/file_transfer.rs:71](</Users/zhaoruiyu/Documents/ChatGPT/mac windows/src/file_transfer.rs:71>)；发送端限制在 14–20 行。

512 MiB 限制只由本地发送程序检查。接收端直接接受远端声明的长度并创建文件，没有累计配额；对端错误实现或连续文件请求可能不断消耗本地磁盘。

复现：接收端接受了长度为 `512 MiB + 1` 的文件清单。测试仅创建空暂存文件，没有真实写入大文件。

影响范围：旧文件模式，需要已认证连接，不等于未经配对即可远程访问。

修复要求：接收端独立核对单文件大小、整组大小、数量、文件名和剩余缓存预算；超过上限在写内容前拒绝，并在写入时持续累计实际字节，处理磁盘空间不足。

## 下一功能的三种实现路线

| 路线 | 优点 | 代价与判断 |
|---|---|---|
| 复用现有复制粘贴体验，新增可靠的普通文件传输 | 符合当前操作方式，复用加密连接与系统文件剪贴板 | **推荐**；需要独立批次、流式落盘、接收确认和会话退出管理 |
| 先做“选择文件—发送—接收文件夹”窗口 | 容易显示进度、取消和结果 | 要建设 GUI 和操作入口，会偏离这次希望直接复制粘贴的习惯 |
| 开启旧 `CROSSDESK_ENABLE_CLIPBOARD` 全量模式 | 看起来改动少 | 上述四项旧文件问题仍存在，还会同时开启普通文本；不宜作为交付方案 |

## 已确认实施的第一版行为

- Windows 资源管理器选择一个或多个文件，Ctrl+C；Mac 收到完成结果后在 Finder 中 Command+V。反方向同样支持。
- 支持任意扩展名的普通文件，包括 PDF、DOCX、XLSX、ZIP、TXT、二进制文件和零字节文件；保留原始字节与可跨平台使用的文件名。接收不自动打开或运行文件。
- 可混选 PNG 和非图片普通文件，作为同一文件批次传输；纯截图/复制图片继续走现有图片模式，单张图片文件继续保留图片表示。
- 建议首版上限：单文件 512 MiB、整组 2 GiB、最多 64 个文件；两端都执行相同限制。此处是资源上限建议，不是已确认的用户要求。
- 首版覆盖普通文件；目录、符号链接/Windows reparse points、云盘未落地占位文件整组跳过并说明原因。目录传输另立后续任务；“剪切”只按复制处理，不删除源文件。
- 每次明确的再次复制可以重试，包括相同内容。断线后的旧剪贴板不自动补发；再次复制从头发送。断点续传留到后续版本。
- 传输期间本地出现新复制，接收完成时保留该本地内容，并返回“已完成传输、未替换剪贴板”的明确结果。
- 接收的文件全部落盘并校验成功才发布，失败时保留原剪贴板。对目标文件夹的最终写入和重名询问仍由 Finder/资源管理器正常粘贴处理。
- 用明确的 `--file-clipboard on|off` 开关和能力协商控制任意文件模式，建议新版两端默认开启，可单独关闭。保持同一配对密钥与 TCP 24920。

## 分阶段工作顺序

### 阶段 A：修复复制事件与接收结果语义

涉及 `src/clipboard/session.rs`、`src/clipboard/mod.rs`、`src/clipboard/windows.rs`、`src/clipboard/macos.rs`。

1. 把 R1/R5 的隔离复现纳入正式回归，先观察失败。
2. 让原生发布返回自己的发布身份，区分本地再次复制和远端写回；只对白名单内的远端表示去重，不能把任意读回内容登记为远端。
3. 工作线程产生结构化的发送、接收、跳过、失败事件；为后续文件确认保留任务 ID。日志只包含数量、大小、状态与原因，不包含文件内容或密钥。
4. 回归截图、透明 PNG、图片文件与新本地复制保护。此阶段应能独立验收。

### 阶段 B：实现可靠、受限的文件批次

涉及新的 `src/file_transfer/` 子模块、`src/protocol.rs`、`src/transport.rs` 和上述公共剪贴板会话。旧 `src/file_transfer.rs` 的调用要么迁移，要么明确关闭，避免保留两套接收语义。

- 按职责拆成清单/文件名、发送、接收暂存、缓存生命周期、回归测试；逐步接入，不做无关重构。
- 建议协议升级为 v6，Hello 分别声明图片和普通文件能力；旧版在握手时明确提示更新两端。
- 文件帧带批次 ID、文件索引和偏移；清单包含名称与长度。每个文件完成时提供 SHA-256，整组完成后才进入校验与发布。
- 加入接受/拒绝、完成结果和取消消息；“发送完成”与“对端已可粘贴”分别显示。新复制替代排队任务；对正在发送的旧任务显式取消，接收端只清理它的暂存目录。
- 文件内容按 16 KiB 分块读取和写入，禁止整批驻留内存。为每方向设置有界队列，目标文件传输额外缓冲不超过 8 MiB；图片解码内存另按现有限制计算。接收主循环不执行长时间磁盘校验，采用流量窗口/背压保证文件 I/O 不堵住键鼠和心跳。
- 同一加密连接复用；控制、心跳和键鼠优先于数据块。持续输入时也要验证文件能推进，避免单方面饥饿。
- 文件以排他方式写入私有批次目录的 `.part`，处理不安全名称、Unicode/大小写等价、源文件发送期间改变、零字节文件、磁盘不足与取消。长度/摘要不一致拒绝整组。
- 维护独立缓存目录和预算；超过预算先拒绝新任务，不删除剪贴板仍引用的内容。完成缓存清理策略须包含正在粘贴场景的实机验收。

### 阶段 C：接入两端、验收和交付

涉及 `src/client.rs`、`src/server/windows.rs`、`src/main.rs`、启动脚本、README/VALIDATION 和 `.github/workflows/crossdesk-input.yml`。

1. 共用一个会话内剪贴板观察器，按位图/文件分派；接收文件用现有 CF_HDROP 与 macOS 文件 URL 发布，不再把多种观察器同时开启。
2. 增加开关、能力协商、版本错误提示及清晰的传输结果日志；两个客户端方向都接入，断线取消任务、回收线程及暂存文件。
3. 原生 Windows CI + Mac CI 执行平台剪贴板测试，制作同版本运行包，继续排除所有配对密钥。
4. Windows 11 与 Apple Silicon Mac 双机完成下列验收后再发布。

## 文件互传的验收标准

| 场景 | 通过条件 |
|---|---|
| PDF/DOCX/XLSX/ZIP/零字节/中文名称，多文件与混合图片文件 | 双向粘贴成功，数量、文件名和 SHA-256 一致 |
| 不同目录同名、大小写等价、Unicode 等价文件名 | 每个文件都保留或整组明确拒绝，绝无静默覆盖 |
| 单文件大小、总大小、数量、恶意长度/名称 | 在分配或写入超额内容之前拒绝，现有剪贴板保留 |
| 文件中途断开、源文件改变、取消、磁盘写入失败 | 没有不完整文件被发布，暂存可回收，失败原因明确 |
| 接收过程中本地复制 B，发布后立即复制 C | B/C 按时序受到保护；新的本地复制不被当作回传吞掉 |
| 被跳过后再次复制相同文件或图片 | 建立新任务并能重试；没有循环回传 |
| 下一批失败、复制文件后延迟粘贴、文件管理器正在粘贴 | 上一批仍可用；缓存清理不破坏文件管理器操作 |
| 双向同时发送大文件，同时跨屏键鼠操作 | 文件内容正确，键鼠和心跳持续工作，无卡键/误断线；记录相比空载的延迟变化 |
| 大于现有图片批次上限的文件传输 | 文件缓冲有明确上限，内存不随整组文件大小增长 |
| 多次重连/退出/休眠唤醒 | 单会话线程数不累积，旧连接不能继续传输，退出释放输入 |

建议按 A → B → C 实施。第一版交付以“任意普通文件复制粘贴完整闭环”为目标；GUI 进度、目录和断点续传各自另开后续范围，避免一次修改协议、缓存、界面和恢复机制后难以定位问题。
