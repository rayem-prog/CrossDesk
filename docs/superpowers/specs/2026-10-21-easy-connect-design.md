# CrossDesk 0.4.0：便捷开启传输

本次目标已按用户 2026-10-21 的要求调整为“方便开始传输，减少操作步骤”。取代旧 GUI 草案中“手动填写 IP、选择密钥文件、不自动连接”的主流程。以下是实施设计，尚未实现。

## 用户流程与交付标准

**第一次：两端打开应用 → Mac 选择自动发现的 Windows → 输入 Windows 显示的六位码 → 连接成功，开始复制粘贴。**

**以后：两端打开应用 → 自动连回已配对设备 → 复制粘贴。**

- 默认启用图片和普通文件双向同步，不要求填写端口、复制 .key 文件或运行终端命令。
- Windows 首次打开显示配对码，Mac 自动显示附近的 Windows；多台时由用户选择，不能擅自配对第一台。
- 首次成功配对后默认记住设备并开启“打开应用时自动连接”；可以在设置中关闭。
- 主页展示设备名、寻找设备/等待配对/连接中/已连接状态，以及连接/断开按钮。日志、地址、密钥导入和同步开关收进“高级设置”。
- 用户点击断开后，本次运行不再自动连接；点击连接或下次打开才恢复。
- IP 改变后重新发现地址，沿用已保存配对；不能因为同名设备出现就信任它。
- Mac 辅助功能、本地网络以及 Windows 防火墙的必要系统授权有就地引导；应用不能绕过这些系统授权。
- “已连接”必须等认证、v6 协商与输入/剪贴板初始化完成，不以进程存活、发现设备或 TCP 接通代替。

## 推荐路线

采用“局域网自动发现 + 一次配对码 + 记住设备 + 应用启动时连接”。仅把旧命令包成按钮仍会留下 IP 和密钥搬运；完全无确认配对会连接到未经用户选择的设备。这两条路线均不能满足本次目标。

GUI 复用现有 Tauri / React，但首页改为设备与连接流程。旧界面的滚轮、键盘映射等放进高级设置，不把它们作为开始传输的前置步骤。

## 全局约束

- 产品目标版本 0.4.0；传输继续使用协议 v6、TCP24920 和现有 Noise 加密。
- Windows 为键鼠服务端，Apple Silicon Mac 为客户端；图片与普通文件双向同步。
- 文件限制保持 512 MiB/文件、2 GiB/批次、64 文件和 4 GiB 缓存；不增加文件夹或断点续传。
- 正常连接流程不要求用户输入 IP、端口、密钥路径或终端命令。
- 配对码六位数字、120 秒有效、最多五次尝试、同一窗口最多一个握手；成功、取消、过期后立即关闭配对窗口。
- 六位码仅用于 PAKE 引导，不能明文发送，不能直接哈希后充当长期配对密钥。
- 长期密钥为 32 字节随机数，保存在用户数据目录；配对码、长期密钥不得进入配置日志、发现广播、UI 日志或交付包。
- 第一版只管理一组 Windows/Mac 配对；新增设备必须经首次配对流程，已有配对不被静默替换。
- 发现只提供地址线索，信任必须来自已保存密钥或当次正确的配对码。
- 主动断开抑制本次运行的自动重连；网络掉线可重试，但不重放离线剪贴板内容。
- 关闭应用必须停止发现、配对监听和服务子进程；不开机自启、不后台常驻。
- 自动化只使用临时数据、假子进程与加密回环连接，不控制用户设备或覆盖日常剪贴板。

## 模块分工

为保证各部分可以独立验证，拆为三个依次交付的子项目：

1. **首次配对与记住设备**：短码验证、密钥传递、持久化。命令行测试入口和回环测试即可独立验证。
2. **自动发现与连接策略**：局域网公告、设备列表、地址变化、已配对设备重连。独立测试状态机和网络适配器。
3. **便捷启动界面和运行包**：将前两项接到首页，双击打开即进入流程；交付 Windows/Mac 包。

## 网络和配对设计

- 正常传输端口保持 TCP24920；mDNS 使用 UDP5353。初次配对额外使用短时 TCP24921，仅配对窗口有效时监听。本项明确取代旧草案“不增加任何监听端口”的约束，避免修改已验证的 v6 Noise 数据通道来复用配对帧。
- Windows 公告 `_crossdesk._tcp.local.`，包含稳定随机 device_id、role=windows、protocol=6、服务端口、是否开放配对以及配对端口。广播不含码、密钥或剪贴板。
- 配对连接先交换有长度上限的版本、设备 ID、窗口随机 nonce 和 SPAKE2 消息；身份串绑定这次窗口及双方 ID。配对码正确后得到引导密钥，使用现有 Noise 握手做密钥确认；长期随机密钥只在该加密连接内发送。
- 选用 spake2 0.4.0 API 路线和 HKDF-SHA256，禁止自行实现曲线或 AEAD。该 crate 的文档明确说明没有独立第三方审计；不能把“使用标准算法”写成“本实现已审计”。配对网络消息和密钥确认需要单独审查与负向测试。
- Windows 使用已保存的长期密钥，缺失时自动生成。Mac 收到后先写待确认记录，确认完成才标记已配对；网络或磁盘中途失败保留原已配对记录，首次未完成时显示重试。重试复用未被用户重置的 Windows 长期密钥，不留下半份公开信任记录。
- 两端数据写入私有用户目录，Unix 权限目录 0700/文件 0600；Windows 使用当前用户 AppData 的访问控制。GUI 只拿设备名和状态，不拿长期密钥字节。
- 从旧包导入现有 .key 仍可用，入口在高级设置；新用户不用搬文件。0.3.0 老客户端无法参与短码发现配对，但已有密钥的 v6 手动连接继续兼容。

## 自动连接策略

应用打开且已有配对：Windows 启动服务并公告；Mac 根据稳定 ID 找到当前地址，再使用原密钥认证。最后地址只作为发现失败时的备选，不能用于建立新信任。

未配对：Windows 在前台打开后提供 120 秒配对窗口；Mac 列设备，用户选择后输入码。超时后显示“重新生成配对码”，不无限自动续期开窗。成功后双方自动开启传输。

每批候选最多八个地址，每次一个服务子进程，失败按 1/2/4/8 秒退避并封顶；认证失败停止自动尝试并显示重新配对入口。主动断开优先于发现和重试事件，旧进程退出后才可重启。找不到设备超过八秒时显示刷新与可折叠的手动地址入口，而不是要求所有人先填 IP。

## 验收

1. 清空两端应用自己的测试数据，在同一局域网完成首次流程，全程不打开终端、不复制密钥文件、不查 IP。
2. 关闭后再打开两端，直接连接；Windows 改 IP 后仍能重连。
3. 手动断开后等待三轮自动重试周期，仍保持断开；点击连接才恢复。
4. 多台 Windows、错误码、过期码、五次错误、伪造同名公告、损坏消息和磁盘写入失败，均不能建立错误信任或泄露密钥。
5. 连上后截图、PNG/JPG 文件、PDF 在两端原生粘贴；运行现有 129 MiB 加密传输验收。
6. 无网络、mDNS 被阻止、系统权限拒绝时有可操作的反馈；重连十次/退出后无残留服务、监听和发现线程。
